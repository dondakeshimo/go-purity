# メモリ書き込み／エイリアス解析の現状とロードマップ

純粋性判定のうち「副作用がないこと」の中核は、メモリ書き込みが「観測可能か（関数外部から見えるか）」の判定である。本ファイルは現状の方式と、将来のエスケープ解析導入方針を記す。

## 現状: ルート分類（root classification）

書き込み先（アドレス）の「根（root）」を SSA 値グラフ上で追跡し、観測可能性を判定する。`purity/shared.go` の `rootOf` が実装。

| 根 | 判定 | ReasonCode |
|---|---|---|
| `Global`（パッケージ変数） | `IMPURE` | `RStoreGlobal` |
| 参照型 `Parameter`（ポインタ・スライス・マップ引数） | `IMPURE` | `RStoreParam` / `RMapUpdate` |
| `Alloc` / `MakeSlice` / `MakeMap`（関数内ローカル割当） | `PURE` | （なし） |
| 分類不能（呼び出し戻り値・`FreeVar`・`Phi` 混合等） | `IMPURE`（暫定） | `RStoreOther`（`Provisional`） |

`append`/`copy`/`clear`/`delete` も同様に、第 1 引数（書き込み先）の根で判定する。ローカルなら `PURE`、参照型引数・グローバルなら `IMPURE`、分類不能なら `IMPURE`（`Provisional`）。

### なぜ「ローカル書き込みは PURE」とみなせるか

関数ローカルな `Alloc`/`MakeSlice`/`MakeMap` への書き込みは、その割当が関数外へ漏れない限り観測されない。ローカル割当が漏れる（エスケープする）経路は必ず以下のいずれかを伴い、それぞれ他の規則で捕捉される。

1. グローバルへの代入（`g = &x`）→ `RStoreGlobal`
2. 参照型引数への代入（`*p = &x`）→ `RStoreParam`
3. チャネル送信（`ch <- &x`）→ `RSend`
4. 他関数への引数渡し → その関数の純粋性で捕捉（不純/`UNKNOWN` なら伝播）
5. `return &x` → 新規ヒープ割当の返却であり副作用ではない

したがって、現状の「ルート分類」は、完全なエスケープ解析を行わずとも実用上は健全（sound）である。

## 現状の制約（既知の誤検出）

- 分類不能（`rootOther`）アドレスへの書き込みは一律 `IMPURE`（`Provisional`）として報告する。実際にはローカル割当を指す場合があり、誤検出となる。
  - 例: `p := getPtr(); *p = 1`（`getPtr` が `*int` を返す）。呼び出し戻り値の行き先を追跡しないため、`getPtr` が新規割当を返すことを証明できず `IMPURE` になる。
- 完全なエスケープ解析（後述）を導入すれば、この種の誤検出を `PURE` に緩和できる。

## ロードマップ: エスケープ解析の段階導入

`purity/shared.go` の `rootOf` を、より精緻な**自作の保守的エスケープ解析**へ段階的に差し替える。

1. **関数間要約**: 各関数について「どのポインタ引数/到達可能領域へ 書き込む・読み出す・返す・漏らす」を要約し、呼び出しをまたいで伝播する。
2. **呼び出し戻り値の行き先追跡**: 純粋な呼び出しの戻り値が「新規割当」であることを証明し、`rootOther` の書き込みを `PURE` へ緩和する。
3. **ローカル割当のエスケープ追跡**: `Alloc` のアドレスがどこへ流れるかを追跡し、観測可能性を精緻化する。

> 注: `golang.org/x/tools/go/pointer`（Andersen ポインタ解析）は deprecated のため採用しない。

## コールグラフ: CHA を採用する理由

- 純粋性解析は、動的呼び出し（インタフェース・関数値）の「取りうる全呼び出し先」を検査する必要があり、**過大近似（sound）なコールグラフ**が要る。
- CHA はインタフェースの全実装を含む過大近似で、ライブラリ（`main` なし）でも機能する。
- VTA はより精緻だが、型フローが発生しない引数について実装を刈り込むため、ライブラリでは不純な実装を見落とす（過小近似）。よって不採用。
